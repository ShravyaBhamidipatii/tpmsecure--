01 — the building blocks

Four ideas, explained plainly

Everything else on this page is built from these four pieces. Each has a "go deeper" button if you already know the term and want the precise technical detail.

1

Disk Encryption

the idea of scrambling your files

Think of it like: writing your diary in a secret code. If someone steals the notebook, they just see gibberish unless they have the key to decode it.

Your computer's storage holds this scrambled version of your files at all times. Something has to hold the "key" that turns the gibberish back into readable data — and that something needs to be trusted.

Full-disk encryption typically uses a symmetric cipher (e.g. AES-256-XTS) over the entire block device. The actual encryption key is itself usually wrapped/encrypted by a key-derivation function, so the real secret you protect is much smaller than the disk itself.
2

LUKS

Linux Unified Key Setup

Think of it like: a specific, standardized brand of lock. Anyone can recognize a LUKS-encrypted disk and knows exactly how to interact with its lock, even across different tools and distributions.

LUKS is the standard way Linux systems actually implement disk encryption. It manages the scrambled data, stores metadata about how it's locked, and supports multiple ways to unlock the same disk — a password, a key file, or (relevant here) a hardware chip.

LUKS2 stores a header with keyslots — each keyslot is an independently encrypted copy of the master key, unlockable by a different method. This project uses cryptsetup luksFormat and luksOpen, then adds a TPM2-backed keyslot via systemd-cryptenroll.
3

TPM

Trusted Platform Module

Think of it like: a tiny, tamper-resistant safe soldered onto the motherboard. It holds the key to your diary, but it only hands it over automatically if the computer looks exactly the way it's supposed to.

Instead of you typing a password every single boot, the TPM can hold the disk's unlock key and release it automatically — but only if it recognizes the state of the machine as trustworthy. If something about the boot process looks different, it refuses.

A TPM 2.0 chip provides a hardware root of trust: key sealing, random number generation, and measured boot support. Keys can be sealed to specific PCR policies so they only unseal under a matching platform state. This project uses tpm2-tools and swtpm (software TPM) for development.
4

PCR

Platform Configuration Register

Think of it like: a fingerprint the TPM builds up as your computer boots — one number that summarizes firmware, bootloader, and OS state. Change any of those, even slightly, and the fingerprint comes out completely different.

This is the actual thing the TPM checks before releasing the key. If a security update changes firmware or the bootloader, the fingerprint changes too — and the TPM, correctly, no longer recognizes the machine as the one it originally trusted.

PCRs are extended (never directly overwritten) via PCR_new = SHA256(PCR_old || measurement) during boot, forming a hash chain. This project reads/predicts PCR state with tpm2_pcrread and systemd-pcrlock predict.
Put together: disk encryption scrambles your files → LUKS manages the lock → the TPM holds the key → it only releases that key if the PCR fingerprint still matches. That last link is exactly where things go wrong today.

02 — the problem

A sharp edge nobody plans for

Now that the four pieces are on the table, here's exactly where they collide.

what should happen

You install a routine firmware or bootloader update. The system reboots. The PCR fingerprint is recalculated, the TPM releases the key, and everything unlocks normally.

what actually happens

The update legitimately changes the boot measurements. The new PCR fingerprint doesn't match what the TPM originally sealed the key against. The disk refuses to unlock — with no warning beforehand.

03 — how it works

Four gates, in order

Click each stage to see what it actually checks.

01

Pre-flight prediction +

Before any update is applied, TPMSecure predicts what the resulting PCR fingerprint would be and compares it against what's currently sealed — catching a coming lockout while there's still time to warn the user.
02

PCR verification +

After the update completes, the real PCR fingerprint is checked against what was predicted. A mismatch here means something unexpected happened — re-enrollment stops immediately.
03

Device authentication +

A matching fingerprint alone isn't proof of identity — it could in principle be satisfied by different hardware presenting the same measurements. This gate requires a valid TPM-backed device certificate too.
04

Automatic re-enrollment +

Only once both checks pass does the system reseal the disk key against the new, verified boot state — automatically, with no manual recovery key entry.

05 — who this helps

Real situations this prevents

TPM-sealed disk encryption shows up in more places than people realize — anywhere full-disk encryption plus a hardware root of trust is used.

Remote servers

A server that fails to unlock after a routine patch means a physical visit to a data center, or a slow out-of-band recovery process.

impact: hours to days of downtime avoided

Developer workstations

Full-disk encryption is standard on security-conscious dev laptops. An unplanned lockout costs a day recovering keys instead of shipping code.

impact: no interrupted sprints

Security teams & audits

The device certificate gate closes a real gap: a PCR match alone can't tell the original trusted hardware apart from a different device presenting the same measurements.

impact: independent, verifiable identity check

Healthcare & regulated devices

Encrypted patient-record systems and medical devices often can't tolerate an unplanned reboot into a locked state — predictable, auditable unlock behavior matters.

impact: fewer compliance-relevant incidents

Edge & IoT fleets

Devices deployed in the field can't always be physically accessed to re-enter a passphrase. Automatic, verified re-enrollment keeps fleets self-healing.

impact: fewer truck rolls

Personal machines

Anyone using LUKS + TPM on a personal laptop benefits from not losing access to their own files after a routine, legitimate OS update.

impact: no surprise recovery-key hunt

06 — for researchers & reviewers

Technical implementation detail

The plain-language explanations above map directly onto these commands and mechanisms — nothing here is simplified further.

LUKS2 volume + TPM2 keyslot enrollment

The disk is formatted and opened as a standard LUKS2 volume, then a TPM2-backed keyslot is enrolled and bound to a specific PCR set.

# format + open cryptsetup luksFormat /dev/sdXN cryptsetup luksOpen /dev/sdXN tpmsecure_vol # bind unlock to current PCR state systemd-cryptenroll --tpm2-device=auto \ --tpm2-pcrs=0+1+2+3+4+5+6+7 /dev/sdXN

Pre-flight PCR prediction

Before an update, the predicted post-update PCR state is computed from the boot event log and compared against the currently sealed policy.

# build boot-event policy, then predict systemd-pcrlock make-policy systemd-pcrlock predict

Device identity certificate (original contribution)

A TPM-resident primary key anchors a device identity certificate, checked independently of PCR state before re-enrollment proceeds.

# TPM-resident key + self-signed device cert tpm2_createprimary -C o -g sha256 -G rsa -c primary.ctx openssl genrsa -out device_key.pem 2048 openssl req -new -key device_key.pem -out device.csr \ -subj "/CN=tpmsecure-device" openssl x509 -req -in device.csr -signkey device_key.pem \ -out device_cert.pem -days 365 # verification against known-good fingerprint openssl x509 -in device_cert.pem -noout -fingerprint -sha256

Validated failure mode (Scenario B)

A deliberate PCR extension was used to simulate a genuine boot-state change, confirming the TPM correctly refuses to unseal and cryptsetup falls back to passphrase authentication rather than failing silently.

$ tpm2_pcrextend 3:sha256=0000...0000 $ cryptsetup open /dev/loop0 testcrypt2 Failed to unseal secret using TPM2: State not recoverable Enter passphrase for /home/.../testdisk.img: _

Known implementation limitation

systemd-pcrlock policy-based TPM sealing showed OR-policy session instability under the swtpm software TPM emulator used for development. Direct PCR-list enrollment (--tpm2-pcrs=) is used for the actual disk seal, while systemd-pcrlock predict is retained for the pre-flight prediction stage. This is documented rather than hidden, since it reflects a genuine emulator constraint rather than a design flaw.

07 — questions

Common questions

Does this replace LUKS or the TPM? +

No — it sits on top of both. LUKS still does the actual encryption, and the TPM still does the actual sealing. TPMSecure adds prediction, verification, and identity-checking around that existing mechanism.

What happens if the prediction is wrong? +

The system never trusts the prediction blindly — it always re-verifies the real, observed PCR state after the update actually happens. Prediction only provides an early warning, not the final decision.

Why is a device certificate needed if PCRs already match? +

PCR values describe the state of software and firmware — not which physical device produced them. The certificate ties re-enrollment to a specific piece of hardware, closing that gap.

What if both checks fail? +

The system refuses automatic re-enrollment entirely and falls back to the normal manual passphrase — the same safety net that exists today, just reached only when genuinely needed.
